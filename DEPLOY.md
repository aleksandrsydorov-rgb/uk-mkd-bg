## Шаг 1. Обновление приложения

Ожидаемая база до этого пакета: 208 миграций, последняя версия `20261130337600`. После четырёх файлов ниже: 212 миграций, версия `20261130338000`. Если фактическая версия другая, миграции не применять и образ не переключать.

Перед применением сверить:

```sql
select count(*) as migration_count, max(version) as head
from supabase_migrations.schema_migrations;
```

1. Снять резервную копию базы.
2. Применить недостающие миграции по имени файла, строго после уже стоящей версии:
   - `20261130337700_portal_legal_revisions.sql`
   - `20261130337800_portal_legal_acknowledgements.sql`
   - `20261130337900_portal_legal_admin.sql`
   - `20261130338000_portal_legal_complex_installation.sql`
3. Снова выполнить запрос выше. Ожидаемый результат: `212` и `20261130338000`.
4. Включить проверку входа через настройку роли `authenticator`, а не через переменную контейнера. Управляемый Supabase не даёт задать `PGRST_DB_PRE_REQUEST` в окружении PostgREST. Миграция только выдаёт право на `public.portal_legal_pre_request` и сама проверку не включает.

   Сначала прочитать действующее значение, не затирая его:

   ```sql
   select unnest(s.setconfig)
   from pg_db_role_setting s
   join pg_roles r on r.oid = s.setrole
   where r.rolname = 'authenticator';
   ```

   Если `pgrst.db_pre_request` нет, включить функцию напрямую:

   ```sql
   alter role authenticator set pgrst.db_pre_request = 'public.portal_legal_pre_request';
   notify pgrst, 'reload config';
   ```

   Если значение уже есть, например `public.previous_pre_request`, поведение прежнего обработчика сохраняется. Нужна отдельная функция в `public`, которую может выполнять роль запроса (`anon` и `authenticated`). Она не должна писать в таблицы: PostgREST вызывает её в той же транзакции, а для стабильных функций транзакция только на чтение. Сначала вызывается прежний обработчик, затем проверка документов:

   ```sql
   create or replace function public.portal_legal_pre_request_chain()
   returns void
   language plpgsql
   security definer
   set search_path = public
   as $$
   begin
     perform public.previous_pre_request();
     perform public.portal_legal_pre_request();
   end;
   $$;

   revoke all on function public.portal_legal_pre_request_chain() from public;
   grant execute on function public.portal_legal_pre_request_chain() to anon, authenticated, authenticator;

   alter role authenticator set pgrst.db_pre_request = 'public.portal_legal_pre_request_chain';
   notify pgrst, 'reload config';
   ```

   Имя `previous_pre_request` заменить на функцию из прочитанного значения. После `NOTIFY` в журнале PostgREST должна быть строка `Config reloaded`.

   Сразу после миграций реестр пуст, обязательной редакции нет, и тот же защищённый вызов отвечает 200. Проверка отказа нужна перед публикацией обязательной редакции: JWT собственника, который её ещё не принял:

   - `POST /rest/v1/rpc/list_my_owned_properties` возвращает 403 и `portal_legal_acceptance_required`;
   - `POST /rest/v1/rpc/portal_legal_acceptance_status` и `POST /rest/v1/rpc/public_portal_legal_current` остаются доступны;
   - после `portal_legal_record_acknowledgements` тот же список апартаментов возвращает 200.

   Вернуть прежнее значение теми же двумя командами. Если настройки не было:

   ```sql
   alter role authenticator reset pgrst.db_pre_request;
   notify pgrst, 'reload config';
   ```

   Если она была, `alter role authenticator set pgrst.db_pre_request` возвращает прочитанную строку, затем снова `NOTIFY`. Пока настройка снята, защищённый вызов снова отвечает 200. Это проверено на локальном PostgREST 12.2.12. Перед публикацией обязательных условий то же чтение, включение и HTTP-проверку нужно повторить на VPS: облачный проект и рабочая база этой проверкой не менялись.

   Эта проверка закрывает Data API. Она не закрывает Storage и Realtime. Маршрут квитанции сначала вызывает `get_payment_receipt` через Data API, поэтому до принятия редакции сам маршрут получает тот же отказ. Realtime кабинет не использует.
5. Поставить образ приложения и переключить трафик. Ключ `service_role` остаётся на сервере. В браузер он не попадает.
6. Пока обязательная редакция не опубликована, проверить вход собственника: кабинет, его апартамент, начисления и история оплат открываются. Это штатное состояние сразу после обновления.

## Шаг 2. Публикация обязательных условий

Этот шаг делается только после шага 1 и только утверждёнными текстами. Черновик посетителю не виден. Тестовые тексты, учётные записи стендов и приглашения со стенда не загружать.

Перед публикацией редакции с «Требовать принятия» повторить на VPS чтение `pgrst.db_pre_request`, включение или цепочку и HTTP-проверку из шага 1. Отдельно проверить Storage: локальный стенд копии не содержит Storage API, поэтому подпись ссылки там не подтверждалась.

На проде, до публикации обязательной редакции, войти собственником и в кабинете открыть уже опубликованный документ собрания. Кабинет запрашивает подписанную ссылку на 60 секунд через Storage, минуя `portal_legal_pre_request`. Политика Storage пускает собственника к опубликованному документу и не смотрит, приняты ли условия портала. Зафиксировать:

- выдаётся ли ссылка до принятия условий;
- открывается ли она сразу;
- открывается ли та же уже выданная ссылка повторно, пока не истекли 60 секунд.

Если ссылка выдаётся и живёт до срока подписи, так и оставить в протоколе выката: проверка PostgREST этот файл не закрывает. Не публиковать обязательную редакцию, пока эта проверка на проде не записана.

Утверждённые документы публикует администратор комплекса в разделе «Правни документи» / «Юридические документы».

## Публикация через админку

Раздел находится в группе «Документы» и доступен роли «администрация». Для каждого вида видны действующий текст, запланированные редакции, черновики и архив. Дата публикации и дата вступления в силу показываются отдельно. Запланированная редакция начинает действовать в указанную дату по Europe/Sofia.

Публикация — отдельное действие после предпросмотра. Перед ней видны аудитория, дата вступления в силу и последствие для первого входа.

- Условия использования: настройка «Требовать принятия этой редакции». Если она включена у действующей редакции, собственник принимает её до кабинета.
- Уведомление о данных и правилник: только «Предложить ознакомиться». Обязать принять их нельзя.
- Правилник публикуется только с реквизитами акта утверждения. Пока акта нет, проект на 116 апартаментов остаётся черновиком.

Опубликованный текст и вложения не переписываются. Следующее изменение — новая редакция. Публикация записывается с сотрудником и временем.

## Что не переносить на сервер

Локальные проверочные редакции, учётные записи стендов, токены приглашений и адреса локальных стендов в пакет не входят. На сервере после миграций реестр документов пуст, пока управляющая компания не опубликует утверждённые тексты.
