# Описание проекта: платформа управления МКД / ОС (Болгария)

**Рабочее имя репозитория:** `uk-mkd-bg`  
**Объект / контекст:** комплекс Amadeus 11 (Слънчев бряг, България)  
**Правовая рамка:** ЗУЕС (Закон за управление на етажната собственост) и смежное болгарское законодательство  
**Языки интерфейса:** русский, английский, болгарский  

---

## 1. Цель продукта

Цифровая платформа для администрирования многоквартирного здания (этажная собственост) в Болгарии:

- ведение книги собственников и связанных данных по ЗУЕС;
- подготовка и проведение **общих собраний** собственников;
- юридически значимые документы собрания (покана, протокол размещения, протоколы, решения);
- личный кабинет собственника (заявки, опросы, участие в собрании, голосование);
- операционные модули управляющей компании (финансы, заявки, охрана, интернет и др. — по включённым модулям).

Продукт рассчитан на работу **администрации комплекса** и **собственников квартир** в одном здании / комплексе.

---

## 2. Роли пользователей

| Роль | Кто | Основные возможности |
|------|-----|----------------------|
| **Администрация** | сотрудники с ролью «администрация» | собрания, документы, книга собственников, подтверждение регистрации, проведение собрания |
| **Собственник** | лицо из книги / портала по квартире | просмотр поканы, подтверждение участия (очно/онлайн), голосование, заявки, опросы |
| **Представитель** | по доверенности | участие вместо собственника (с лимитами и подтверждением админом) |
| **Прочий персонал** | бухгалтер, инженер и др. | доступ только к своим модулям (не к полному управлению собраниями) |

Важно: администратор комплекса **может не быть собственником** квартиры, но управляет собранием. В кандидатах на процедурные роли его можно указать отдельно (как «Админ»).

## 3. Ключевой процесс: общее собрание

Процесс в интерфейсе разделён по вкладкам собрания.

### 3.1. Информация
- Название, дата, время, место, формат (очно / гибрид).
- Тип собрания: извънредно, отчетно, отчетно-изборно, спешно.
- Фиксация списка собственников на момент поканы (снимок для юридической привязки).
- Проверка смены собственников после фиксации (блокировка регистрации при расхождении).

### 3.2. Покана (ранее «Повестка»)
- Обязательные пункты дневного реда по типу собрания (председатель, протоколист, отчёты, выборы и т.д.).
- Добавление пунктов вручную и из завершённых опросов.
- Для выборных пунктов — **кандидаты**:
  - председатель, протоколист, ревизор: **ровно 3** кандидата;
  - УС / контрольный совет: сначала предложенное число мест **N**, затем **по 3 кандидата на каждое место**;
  - кандидаты из **активных собственников** книги и/или **админа** комплекса.
- Превью текста поканы собирается автоматически из данных собрания и дневного реда.
- Кнопка **«Зафиксировать покану»** — блокирует текст приглашения (версия в БД). Без полного набора кандидатов фиксация запрещена.
- Публикация собрания для собственников.

### 3.3. Приглашения
Порядок по задуманной юридической логике:

1. Система **формирует PDF протокола размещения** поканы (для печати).
2. Админ распечатывает, собирает **подписи 3 собственников**.
3. Загружает обратно:
   - подписанный PDF протокола;
   - **фотоотчёт** о размещении на табло.
4. Подтверждает размещение (место + время).
5. Только после этого доступна кнопка **«Отправить приглашение всем»** — рассылка **внутри системы** (in-app), по числу собственников из книги этажной собственности (без email-рассылки как обязательного канала).

### 3.4. Участники
- Список зарегистрированных / заявленных участников.
- Режим участия: лично / онлайн.
- Представительство: сам / по доверенности.
- Идеальные части (для кворума и голосования).

### 3.5. Проведение собрания
Первый блок — **действия проведения**:

- **Открыть регистрацию** (доступно за **60 минут** до начала; может открываться автоматически при наступлении окна).
- **Начать собрание** (после подтверждённого кворума).

Далее:

**Регистрация**
- Онлайн: подтверждение доступно до **T−49 часов** (затем окно закрывается); подтвердившие онлайн учитываются в кворуме автоматически.
- Очно: регистрация с **T−1 час**; заявки «лично» и «представитель» требуют **подтверждения администратором**.

**Кворум (по идеальным частям, логика ЗУЕС в продукте)**
- Этап 1: порог **≥ 51%**.
- Если через час после назначенного начала кворума нет — переход на порог **≥ 26%**.
- Далее — этап «следующий день» (по правилам продолжения собрания).
- Табло: текущий % / требуемый %, онлайн в кворуме, очно подтверждённые.
- Действия: проверить кворум, зафиксировать проверку, перейти на 26% / следующий день.

**Голосование и завершение**
- Открытие/закрытие пунктов дневного реда.
- Голосование: за / против / воздержался (по идеальным частям).
- Онлайн-участники могут голосовать по вопросам после подтверждения (в т.ч. до «живого» старта — по заложенной логике).
- **Завершить собрание** (после закрытия открытых голосований).

### 3.6. Документы собрания
Архив файлов: покана, протокол размещения, повестка/дневник, протокол ОС, приложения, доверенности и др.

## 4. Прочие модули продукта (кратко)

Помимо собраний платформа включает (в разной степени готовности) модули управляющей компании и кабинета собственника, например:

- книга / реестр собственников, доли, идеальные части, импорт Excel;
- заявки собственников в УК;
- опросы жителей (в т.ч. вынос результата в повестку собрания);
- финансы / бюджет / начисления (по модулям);
- охрана, интернет и другие сервисы здания (по каталогу модулей);
- мультиязычный UI (RU / EN / BG).

## 5. Технологический стек

- **Frontend:** Next.js 16, React 19, TypeScript, Tailwind CSS  
- **Backend / БД / Auth:** Supabase (PostgreSQL, RLS, RPC security definer)  
- **Документы:** генерация PDF на клиенте (jsPDF + html2canvas), хранение в private storage  
- **Деплой / окружение:** локальная разработка + связанная Supabase-база  

Юридически значимые переходы состояний собрания и запись кандидатов / кворума / уведомлений выполняются через **серверные RPC**, а не только через UI.

---

## 6. Юридические состояния собрания (упрощённо)

Черновик → подготовка → **покана зафиксирована** → размещение подтверждено → рассылка в системе → ожидание собрания → регистрация (check-in) → кворум → собрание идёт → завершено → протокол / архив.  
Отдельно: отмена, перенос, блокировки при смене собственника после фиксации списка.

---

## 7. Что уже реализовано (на момент описания)

- Вкладки собрания: Информация / Покана / Приглашения / Участники / Проведение / Документы.  
- Кандидаты из собственников (+ админ), блокировка фиксации поканы без полного набора.  
- Протокол размещения: генерация PDF → загрузка подписанного PDF + фото → подтверждение → in-app рассылка.  
- Проведение: регистрация T−1ч, подтверждение очных админом, табло кворума 51%/26%, старт и завершение собрания.  
- Онлайн-подтверждение с окном T−49ч.  
- i18n RU/EN/BG для ключевых экранов.

## 8. Что нужно от юриста / регуляторная валидация

Просим подтвердить и/или скорректировать под действующее болгарское право:

1. Достаточность **электронной фиксации** поканы и протокола размещения (скан + фото табло).  
2. Может ли **уведомление только внутри платформы** считаться надлежащим по ЗУЕС, или обязательны email / бумага / иное.  
3. Момент включения **онлайн** в кворум и в голосование.  
4. Допустимость кандидатов-админов **без собственности** на квартиру.  
5. Минимальный состав реквизитов протокола ОС и пакета документов для устойчивости решений при оспаривании.  
6. Полный пакет шаблонов на болгарском (покана, протокол размещения, регистрация, протокол ОС, доверенность, политика персональных данных, договор с УК / условия сервиса).
